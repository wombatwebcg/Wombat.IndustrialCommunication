# IEC104 与 ModbusBridge 合并进核心库计划

版本：v0.1（讨论稿）　范围：`Wombat.IndustrialCommunication.Extensions.IEC104`、`...IEC104.ModbusBridge` → `Wombat.IndustrialCommunication`

## 0. 本文回答什么

三个工程目前是「核心库 + 两个扩展程序集」。本文分析把这两个扩展的源码并入核心程序集是否可行、要动哪些地方、按什么顺序动、怎么验证、失败怎么退。协议实现细节不在本文范围，见 `IEC104_三阶段实施计划.md`。

## 1. 现状盘点

### 1.1 三个工程的事实

| 项目 | 目标框架 | 外部依赖 | 规模 | 当前状态 |
|---|---|---|---|---|
| Wombat.IndustrialCommunication（核心） | netstandard2.0 / net8.0 / net10.0 | Logging、System.IO.Ports、System.Reactive、DataTypeExtensions 1.1.1、Wombat.Network 1.1.9 | 214 个公开类型 | 已发布 2.1.56-preview |
| ...Extensions.IEC104 | netstandard2.0 / net8.0 | Wombat.Network 1.1.9、DataTypeExtensions 1.1.1、Logging.Abstractions 10.0.12 | 25 个文件 / 约 4.7k 行 | 未提交（untracked） |
| ...IEC104.ModbusBridge | netstandard2.0 / net8.0 | System.Text.Json 8.0.5 + ProjectReference 到上面两个 | 13 个文件 / 约 2.2k 行 | 未提交（untracked） |

两处关键差异：

1. 核心库多一个 `net10.0` 目标，两个扩展没有。合并后扩展源码必须能在 net10.0 下编译通过。
2. 桥接层已经反向依赖核心库（`ModbusTcpServer`、`DataStore`、`OperationResult`、`Modbus` 命名空间），并且依赖核心 `DataStore` 的 65535 数组上限（`ModbusRegisterMap.MaxAddress = 65534`）。也就是说「扩展不依赖核心」这条边界在桥接层本来就不成立，只在 104 协议层成立。

### 1.2 代码与依赖的具体咬合点

- 104 主站/从站直接使用 `Wombat.Network` 的 `TcpTransportConnection` / `TcpTransportListener`，**没有**走核心的 `TcpServerAdapter`、`DeviceServer`、`IServer`，也没有走 `ChannelManager`。合并只是把源码放进同一个程序集，不改变这条运行路径。
- 桥接层继承核心的 `ModbusTcpServer`，覆写 `ProcessModbusRequest`，读写 `Server.DataStore`，订阅 `DataStoreWrittenTo`。这些全部是核心现有的 public/protected 成员，合并后无需改一行。
- 命名空间全部落在 `Wombat.IndustrialCommunication.Extensions.IEC104[.Protocol|.Model|.Options|.Session|.Transport|.Diagnostics|.ModbusBridge]` 之下。用脚本比对了三棵源码树的类型简单名：核心 214 个、扩展 70 个，**交集为空**，放进同一程序集不会出现类型冲突。
- 核心程序集已有 `IAsyncDisposable` 用法（`ChannelManager`、`ServerHost`），说明 netstandard2.0 下的异步释放接口已由现有依赖提供，104 代码不会引入新的兼容性问题。
- 核心的 `Modbus/Data/DataStore.cs` 当前有一处未提交改动：把 `WriteCoilsDirect` 等四个方法从 `internal` 改成 `public`，理由是桥接层在另一个程序集里调用。**合并后这四个方法可以改回 `internal`**，核心库少 4 个本不该公开的 API，这是合并最直接的技术收益。

### 1.3 与既有约束的冲突

`docs/IEC104_三阶段实施计划.md` 2.1 节和 `docs/IEC104_主站接入指南.md` 第 1 节都写明「不引用 Wombat.IndustrialCommunication」，理由有四条：核心服务端适配器只认 TPKT/MBAP、客户端传输是请求-响应且有 260 字节上限、`OperationResult` 不适合表达遥控拒绝、`ChannelManager` 绑定 `IClient`。

这四条是**运行路径层面**的理由，合并源码并不违反它们——104 仍然用自己的传输与错误模型。但文档措辞必须改，否则下一个人会以为边界还在。合并计划必须包含文档同步，这是硬要求，不是收尾工作。

## 2. 合并到底合的是什么

先把三件事分开，避免把「合代码」和「合架构」混为一谈：

1. **合包**：只发一个 NuGet 包，用户 `using` 后 104 相关类型可见。这是本次目标。
2. **合架构**：让 104 主站接 `IClient`、从站接 `IServer`、重连交给 `ChannelManager`。**本次不做**，做了会退回三阶段计划里论证过的返工。
3. **合版本**：核心、104、桥接统一版本号与发布节奏。合包后自然成立。

因此，合并的验收标准是「一个程序集、一个包、行为不变」，而不是「104 变成 IClient 实现」。

## 3. 目标目录结构

保持命名空间不变，只搬目录，这样搬迁提交里不该出现任何一行 `.cs` 内容改动，评审只需要看文件移动：

```
Wombat.IndustrialCommunication/
  IEC104/
    Iec104Master.cs
    Iec104Slave.cs
    Protocol/        ApciFrame / Asdu / AsduBuilder / Iec104FrameParser / ...
    Model/           Iec104Point / Iec104PointTable / Iec104Value / Iec104DataStore / ...
    Options/         Iec104MasterOptions / Iec104SlaveOptions
    Session/         Iec104SessionBase / Iec104MasterSession / Iec104SlaveSession
    Transport/       IIec104Link / Iec104TcpLink
```

命名空间与目录不一致（`...Extensions.IEC104` vs 目录 `IEC104`）是刻意的：如果同时改目录和命名空间，搬迁提交就无法用「文件移动 + 零内容改动」来验证，出问题也定位不到是哪一步引入的。

## 7. 备选方案

- **方案 B：不合并，只统一仓库与版本。** 参照蓝牙扩展的现状（独立 csproj + ProjectReference 核心），把两个扩展保留为正式工程，统一版本号与发布流程。优点是核心包不变重、AOT 干净；缺点是多包发布、104 与核心的版本兼容矩阵要自己维护。如果用户在意核心包体积，这是更稳的路。
- **方案 C：104 并入核心，桥接保留独立程序集。** 104 层只依赖 Wombat.Network，并入零新增依赖；桥接带 JSON 配置与应用装配逻辑，留作可选包。这是「合包」与「控依赖」的折中，代价是桥接仍需引用核心（本来就引用），发布时多一个包。

推荐：若目标是「一个包装下 104 全链路」，走本计划（方案 A，D2 选 A、D5 选 3.0.0 或 2.2.0）；若更在意核心包纯净，走方案 C。

### 10.2 必须修的一处命名空间遮蔽

新增 `Wombat.IndustrialCommunication.Extensions.*` 命名空间后，核心原有的三处相对写法 `Extensions.DataTypeExtensions.EndianFormat.ABCD` 的解析路径被改变：

- 改动前：`Extensions` 在 `Wombat` 层解析到包命名空间 `Wombat.Extensions`，整串等价于 `Wombat.Extensions.DataTypeExtensions.EndianFormat`；

涉及文件与行：`Modbus/ModbusRTUClientBase.cs:22`、`Modbus/ModbusTcpClientBase.cs:22`、`PLC/S7/S7Communication.cs:88`。修法是改用文件顶部已有的 `using Wombat.Extensions.DataTypeExtensions;` 导入的 `EndianFormat`，不再写相对限定名。这是本次搬迁唯一的源码内容改动，且只发生在核心原有文件上。

**后续影响**：如果调用方在 `Wombat.IndustrialCommunication.*` 命名空间内也写了 `Extensions.DataTypeExtensions...` 这种相对限定名，升级后同样会 CS0234。发布说明里需要提示改用完全限定名或 `using`。
