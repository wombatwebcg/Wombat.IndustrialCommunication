# Iec104Probe 探测闪退诊断与 P0/P1 改造

适用对象：现场用 `tools/Iec104Probe` 探测第三方 104 从站、遇到"双击后一闪就没了"的人。
本文记录问题定位过程、根因清单，以及 P0（工具层兜底）与 P1（会话层序号容错）两批改动的实际范围与验收结果。

---

## 1. 现象与结论

现象：`Iec104Probe` 探测内置从站（自测模式）正常，改成探测现场已有的从站时，窗口一闪而过，或者只剩一句"探测失败"。

结论分三层：

1. **绝大多数"闪退"其实是"秒退"**。探针是控制台程序，失败时打印一行 `探测失败：xxx` 后以退出码 1 结束，进程本身没有崩。双击运行时控制台宿主随进程退出立即关闭，肉眼看到的就是"闪退"。
2. **协议层有真实的健壮性缺陷**，会让"刚建链就断"，看起来更像崩溃：接收序号 N(S) 严格比对，装置计数器不归零或激活前已上送帧就会立刻断链。
3. **工具层没有任何兜底**：没有全局异常处理、没有日志文件、没有结束前等待、没有失败现场回放。所以即使真崩了，也留不下任何证据。

---

## 2. 诊断过程

用一个 Python 写的假从站模拟现场装置的五种常见行为，逐个跑探针，记录改动前的表现。假从站在 24041/24061/24062/24063 端口上分别起，避免端口复用互相抢占。

| 模拟场景 | 改动前探针输出 | 退出码 |
|---|---|---|
| 端口无监听 | `探测失败：由于目标计算机积极拒绝，无法连接。` | 1 |
| 接受连接后立刻关闭（装置只允许一个主站） | `[链路] Disconnected 链路断开` + `探测失败：远程主机强迫关闭了一个现有的连接。` | 1 |
| 发完脏数据后断开 | `探测失败：对端关闭连接。` | 1 |
| STARTDT con 之前先上送一帧 I 帧 | `探测失败：接收序号不连续：期望 0，实际 1。` | 1 |
| 装置计数器跨连接保留，首帧 N(S)=5 | `探测失败：接收序号不连续：期望 0，实际 5。` | 1 |
| 装置提前确认，N(R) 超过已发帧数 | `探测失败：确认序号越界：N(R)=3，已确认 0，未确认 1。` | 1 |
| 不回 STARTDT con | 15 秒后 `探测失败：STARTDT 确认超时。` | 1 |

补充：公共地址（`--ca`）填错时不会闪退，而是把该装置的 ASDU 全部静默丢弃，30 秒总召超时后退出 1，只有一句 `完成=False`。这类"不闪退但没结果"的情况更费时间，所以 P0 里加了分阶段输出和提示。

## 3. 根因清单

### 3.1 工具层（`tools/Iec104Probe/Program.cs`）

| 问题 | 位置 | 后果 |
|---|---|---|
| `Main` 没有全局 `try/catch` | 改造前 `Main` 直接串联解析与探测 | 任何漏网异常都以未处理异常方式结束进程，只剩一闪而过的窗口 |
| 点表加载在 `try` 之外 | `RunProbeAsync` 首行 `LoadPointTable` | CSV 被占用、路径不可读等直接结束进程，无提示 |
| 失败时主站不释放 | 改造前只在成功路径 `DisposeAsync` | 失败路径靠进程退出兜底，放进宿主后会漏连接 |
| 无日志 | 全文件 | 现场只能靠截图，无法回传断链前后帧 |
| 退出即关窗 | 全文件 | 双击运行看不到结果 |
| 帧追踪需事先加 `--trace` | `if (options.Trace) master.FrameTraced += ...` | 出问题时往往没开，重跑未必能复现 |
| 自测模式退出码恒为 1 | `RunCommandTestAsync` 尾部 `return false`（遥控测试被注释） | 自测成功也报失败 |

### 3.2 会话层（`Wombat.IndustrialCommunication/Iec104/Session/Iec104SessionBase.cs`）

1. **N(S) 严格比对直接断链**（`HandleInformationAsync`）。装置计数器跨连接保留、激活前已上送帧、链路丢帧，任意一种都会命中 `接收序号不连续`。这是现场最常见的"刚连上就断"。
2. **激活前的 I 帧被丢弃但不推进 `_receiveSequence`**（`!DataTransferActive` 分支只 `DroppedFrames++`）。装置那边计数器已经走了，我方还停在 0，下一帧必然错位。
3. **N(R) 越界直接断链**（`Acknowledge`）。部分装置会提前或越界确认，协议上属于装置问题，但不该让整条链路报废。

### 3.3 装置侧（无法改动，只能适配）

- 只允许一个主站连接，第二个连接被拒或被踢。
- 计数器不按连接归零。
- 公共地址与默认 1 不一致。
- 建链慢于 t0（30 秒）。

## 4. P0：工具层兜底

改动文件：`tools/Iec104Probe/Program.cs`（新增 `ProbeLog`、`FrameRing` 两个内部类型）。

### 4.1 全局兜底与日志

- `Main` 拆成 `Main` + `RunCoreAsync`。`Main` 统一 `try/catch`，任何异常写日志后返回 1，不再让进程无提示消失。
- 订阅 `AppDomain.CurrentDomain.UnhandledException` 与 `TaskScheduler.UnobservedTaskException`。后者会 `SetObserved()`，避免后台任务异常在进程退出时升级。
- `ProbeLog` 用 `TeeWriter` 接管 `Console.Out`/`Console.Error`：控制台看到什么，日志文件就有什么，异常带完整堆栈。默认写到程序目录 `logs/Iec104Probe-yyyyMMdd-HHmmss.log`，目录不可写时退回临时目录 `Iec104Probe-fallback.log`；`--log <path>` 可覆盖。
- `Console.OutputEncoding = Encoding.UTF8` 失败不再致命（输出被重定向到某些宿主时会抛 `IOException`）。

### 4.2 结束前等待

`WaitBeforeExit`：未加 `--no-pause`、且标准输入输出都没有重定向时，结束前打印"按任意键退出…"并 `Console.ReadKey(true)`。双击运行不会闪退，管道/脚本调用不受影响。

### 4.3 分阶段输出与提示

- 输出改成 `[1/3] 连接` → `[2/3] 链路已激活，开始总召` → `[3/3] 总召结束，收到 N 点`，能一眼看出断在哪一步。
- `PrintHint` 按异常文本给出可执行提示，例如：
  - `积极拒绝` → 端口没监听，查从站是否启动、端口号、防火墙。
  - `强迫关闭` / `对端关闭连接` → 装置可能只允许一个主站，先断开已有主站。
  - `STARTDT` → 查公共地址（`--ca`）、端口，或装置要不要先完成初始化。
  - `接收序号不连续` / `确认序号越界` → 装置计数器与协议约定不一致，默认已自动重对齐。
- 点表加载失败不再带崩进程，单独报 `点表加载失败` 并返回 2。

### 4.4 失败现场回放

- 新建 `FrameRing`，容量 100，**始终**记录收发帧（`EnableTrace` 常开，打印与否由 `--trace` 决定）。
- 任何失败路径 `DumpRecentFrames` 打印最后 100 帧；一帧都没收到时直接提示"链路可能在建链阶段就被对端关闭"，这一条正好区分"装置拒绝连接"和"装置收了但没回应"。

### 4.5 其它

- 主站释放移入 `finally`，释放失败只记日志。
- `RunCommandTestAsync` 尾部改为返回 `true`：遥控测试目前是注释掉的，原先固定返回 `false` 导致自测模式退出码永远是 1。

## 5. P1：会话层序号容错

改动文件：`Iec104SessionBase.cs`、`Iec104MasterSession.cs`、`Iec104MasterOptions.cs`、`Iec104Master.cs`。

### 5.1 行为变化

| 场景 | 改动前 | 改动后（默认，`StrictSequence = false`） | 改动后（`--strict`） |
|---|---|---|---|
| N(S) 与期望值不符 | 断链 | 以装置的 N(S) 重新对齐，`SequenceResyncs++`，继续收 | 断链，报 `接收序号不连续` |
| 激活前/停传后收到 I 帧 | 丢弃，不推进序号 | 保持原样丢弃（后续首帧会因重对齐而续接） | 同左 |
| N(R) 大于已发帧数 | 断链 | 按"全部已发帧均已确认"处理，`ClampedAcknowledgements++` | 断链，报 `确认序号越界` |

设计取舍：宽松是默认，因为探针的目的首先是"把点表读出来"，一次序号错位就整条链路作废，代价大于收益；严格校验保留为开关，用于怀疑装置实现有问题时取证。协议一致性检查没有删除，只是从"断链"降级为"计数 + 报告"。

### 5.2 新增接口

- `Iec104MasterOptions.StrictSequence`（`bool`，默认 `false`）。
- `Iec104SessionBase.StrictSequence`、`SequenceResyncs`、`ClampedAcknowledgements`；基类构造函数新增可选参数 `strictSequence`（默认 `false`，从站会话不受影响）。
- `Iec104Master.SequenceResyncs`、`ClampedAcknowledgements` 透传，探针据此打印：

```
链路容错：接收序号重对齐 1 次，确认序号截断 0 次。装置计数器与协议约定不一致，数据仍可用，但建议核对装置实现。
```

### 5.3 探针参数

```
--strict                 严格校验 N(S)/N(R)，序号不符直接断链
--trace                  打印收发帧
--log <path>             日志文件，默认写到程序目录 logs/ 下
--no-pause               结束后不等待按键（脚本调用时用）
```

## 6. 验收记录

改动后重跑同一批假从站场景（`--interrogate 3 --timeout 12`）：

| 场景 | 改动后结果 |
|---|---|
| 首帧 N(S)=5 | 建链成功，总召正常发起，末尾输出 `接收序号重对齐 1 次` |
| 激活前先上送帧，之后 N(S)=1 | 建链成功，不再断链 |
| N(R)=3 越界 | 建链成功，输出 `确认序号截断 1 次` |
| 装置立刻断开 | `探测失败：远程主机强迫关闭…` + 提示"只允许一个主站" + `最近 1 帧`（STARTDT act） |
| `--strict` + 首帧 N(S)=5 | 按预期断链：`接收序号不连续：期望 0，实际 5`，并回放 3 帧，可看到 STARTDT act/con 与总召 I 帧 |

日志文件核对：控制台输出与 `logs/Iec104Probe-*.log` 内容一致，异常带堆栈，空行保留。

构建：`dotnet build Wombat.IndustrialCommunication.sln` 0 错误；`tools/Iec104Probe` 0 错误。104 相关无既有单测，回归依赖上述端到端场景。

## 7. 有意未做的部分

- **P2 项**：`--ca auto` 公共地址自动扫描、探测失败自动重试、报告 JSON 增加链路容错字段。公共地址错目前仍表现为 30 秒总召超时，只是现在有提示语指路。
- **会话层不改动传输**：仍走 `Wombat.Network` 的 `TcpTransportConnection` + `PipeReader`，不接入核心的 `TcpServerAdapter`/`ChannelManager`。这是既定边界，本次不碰。
- **从站侧保持严格判断的口子**：`Iec104SlaveSession` 默认也走宽松模式（基类默认值），但没有对外开放 `StrictSequence`。若后续要严格控制从站收帧，再加选项。
- **未补单元测试**：仓库目前没有 104 单测，本次以假从站端到端验证替代；若要长期防止回归，建议把第 6 节的场景固化成测试工程里的 `IIec104Link` 假实现用例。

## 8. 现场排查顺序

1. 先看窗口最后一屏，或直接打开日志文件；有 `最近 N 帧` 说明链路已经通了，问题在应用层。
2. 只有 `STARTDT act` 一帧 → 装置没回 STARTDT con：查 `--ca`、端口、装置是否已满连接数。
3. 有 STARTDT con 但没有 I 帧 → 查公共地址是否匹配、装置是否需要先做时钟同步或初始化。
4. `接收序号不连续` 只在 `--strict` 下出现属正常，说明装置计数器与协议约定不一致，记录次数反馈即可。
5. 需要给厂家抓帧时，用 `--trace` 重跑一次，日志文件可直接回传。
