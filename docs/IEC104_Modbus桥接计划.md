# IEC104 → Modbus TCP 桥接实施计划

版本：v1.0　　适用工程：Wombat.IndustrialCommunication.Extensions.IEC104.ModbusBridge

## 1. 目标与拓扑

现场 2404 主机是被控站，我们的 104 主站连上去，把缓存里的遥测、遥信镜像到 Modbus TCP 寄存器，下游用 ModbusTcpClient 轮询；遥控通过保持寄存器写入，由桥接层转成 104 遥控下发。

```
现场 104 主机 (2404)
        ↑ 104 主站（本库）
        │
   桥接层（本计划）
        │ Modbus TCP Server (502)
        ↓
下游 SCADA / PLC（ModbusTcpClient 轮询）
```

桥接层不改变任何一侧的协议行为：104 侧仍按 STARTDT、总召、突发、k/w 窗口工作；Modbus 侧是标准从站，被动应答。桥接层只做“缓存镜像 + 命令转发”。

## 2. 已定决策

| 项 | 决策 |
|---|---|
| 命令编码 | 保持寄存器：1=请求合、2=请求分、3=确认合、4=确认分、0=无动作 |
| 遥测编码 | IEEE754 float，双寄存器，字序可配，默认 ABCD |
| 遥信区域 | 1x 离散输入，只读 |
| 遥控区域 | 4x 保持寄存器，可写 |
| 确认窗口 | 30 秒，超时状态置 7 |
| 待确认期间写不同请求值 | 覆盖选择，不执行动作 |
| 默认状态 | 命令通道默认关闭，只读镜像先上线 |

## 3. 工程与依赖

新建工程，避免 104 扩展反向依赖核心库：

```
Wombat.IndustrialCommunication.Extensions.IEC104.ModbusBridge/
  ├─ ProjectReference → IEC104 扩展
  ├─ ProjectReference → Wombat.IndustrialCommunication
  └─ TargetFrameworks: netstandard2.0;net8.0
```

104 扩展保持零核心依赖；桥接工程是唯一同时认识两边的地方。代价是多一个包，以及两边的版本需要一起升级。

核心库直接用 `ModbusTcpServer`：它支持 01/02/03/04/05/06/0F/10 八个功能码，四个区各 65535 点，`DataStore` 的写入事件可以挂遥控。

## 4. 寄存器规划

地址统一采用“基准 + 转发号”的方式，而不是按数组下标。转发号来自 CSV，追加点位时已有地址不变。

| 区 | 地址公式 | 本例范围 | 读写 | 说明 |
|---|---|---|---|---|
| 1x 离散输入 | DiscreteBase + 转发号 | 0..297 | 只读 | 298 个遥信 |
| 3x 输入寄存器 | TelemetryBase + 转发号 × 2 | 0..1635 | 只读 | 818 个 float，每个两点 |
| 4x 保持寄存器（命令） | CommandBase + 转发号 × 3 | 0..11 | 读写 | 4 个遥控，每点命令/状态/原因 |
| 4x 保持寄存器（健康） | HealthBase + 偏移 | 1000..1007 | 只读 | 链路与刷新状态 |

三个基准都可配置，默认 0、0、0、1000。命令区与健康区之间留出 900 个寄存器的间隙，方便以后扩命令点。

### 4.1 命令点布局

每个遥控点占三个连续寄存器：

```
CommandBase + n*3 + 0   命令寄存器（写）   0=无动作 1=请求合 2=请求分 3=确认合 4=确认分
CommandBase + n*3 + 1   状态寄存器（读）   0..9，见 7.2
CommandBase + n*3 + 2   原因寄存器（读）   否定原因码，见 5.3
```

### 4.2 健康区

| 偏移 | 内容 |
|---|---|
| 0 | 104 链路状态：0 断开、1 已连接未激活、2 激活 |
| 1 | 遥测最后刷新距今秒数 |
| 2 | 遥信最后刷新距今秒数 |
| 3 | 已映射遥测点数 |
| 4 | 已映射遥信点数 |
| 5 | 点表版本（映射表 CRC16） |
| 6 | 桥接运行状态：0 停止、1 运行 |
| 7 | 保留 |

健康区是下游判断“数据是否可信”的唯一依据。没有它，断链后下游读到的仍是最后一次的值，看起来完全正常。

## 5. 数据映射

### 5.1 遥测

float 按 IEEE754 拆成两个 16 位寄存器：

| 字序 | 寄存器 N | 寄存器 N+1 | 常见场景 |
|---|---|---|---|
| ABCD（默认） | 高 16 位 | 低 16 位 | 多数国产 SCADA |
| CDAB | 低 16 位 | 高 16 位 | 部分 PLC 与海外组态 |

`DataStore.HoldingRegisters` 与 `InputRegisters` 内部是 int，写入时存 0..65535，读侧按 16 位截断。

### 5.2 遥信

单点直接写 1x。双点（如果有）按“合=1、其余=0”处理，同时在健康区无逐点标志，双点中间态会丢失，这一点写进部署文档。

### 5.3 遥控结果码

| 码 | 含义 |
|---|---|
| 0 | 无 |
| 1 | 从站否定确认 |
| 2 | 超时（选择或确认） |
| 3 | 104 链路不可用 |
| 4 | 命令通道未启用 |
| 5 | IOA 不在允许列表 |
| 6 | 确认值与选择不符 |
| 7 | 点忙 |

## 6. 桥接运行时

### 6.1 更新路径

不要在 104 的 `ValueReceived` 里直接写 `DataStore`。104 突发时一秒可能上千条变化，逐条写会和 Modbus 读请求抢索引锁。

采用脏点集合：

```
104 事件 → 记录 IOA 到脏集合（并发字典，天然去重）
        → 刷写循环每 50ms 取一批
        → 解析地址 → 写 DataStore
```

刷写循环是单线程，同一时刻只有一个写入者，避免同一寄存器被两个线程交替写。

### 6.2 初始镜像

启动时按点表把全部地址初始化：遥测写 0，遥信写 false，命令区写 0，健康区写当前状态。这样下游在第一次总召完成前读到的是一组确定的初值，而不是随机内存。

### 6.3 断链行为

链路状态变化时立即更新健康寄存器 0；断链超过 `StaleTimeout`（默认 30 秒）时，刷新秒数继续增长，下游据此判断数据陈旧。

不默认把遥测值改写为特殊值，因为“0”或“NaN”在下游可能被当成真实值。是否让读请求返回 Modbus 异常码 0x04，作为配置项，默认关闭。

### 6.4 多客户端

`ModbusTcpServer` 本身支持多连接，所有连接共享同一个 `DataStore`。桥接层不区分客户端，只有命令审计需要记录来源时才有影响（见 7.4）。

## 7. 命令通道

### 7.1 触发与清零

订阅 `DataStore.DataStoreWrittenTo`，只处理命令寄存器（地址落在命令区、偏移为 0）。

客户端写入后，桥接层在事件回调内立即把命令寄存器写回 0。核心库的写处理器是先写入 `DataStore`、同步触发事件、再组响应，所以客户端收到写成功时寄存器已经是 0，下一次读取一定是确定值。清零用索引器写入，不会再次触发事件。

### 7.2 编码与状态

命令寄存器（写）：

| 写入值 | 含义 |
|---|---|
| 0 | 无动作，忽略 |
| 1 | 请求合 |
| 2 | 请求分 |
| 3 | 确认合 |
| 4 | 确认分 |

状态寄存器（读）：

| 状态 | 含义 |
|---|---|
| 0 | 空闲 |
| 1 | 选择中（等待设备确认） |
| 2 | 待确认合 |
| 3 | 待确认分 |
| 4 | 执行中 |
| 5 | 成功 |
| 6 | 被拒绝 |
| 7 | 确认超时 |
| 8 | 未启用 |
| 9 | 点忙 |

状态必须区分“待确认合”与“待确认分”。寄存器回 0 只表示写入被消费，操作员要靠状态寄存器确认自己请求的是哪个方向，否则二次确认没有意义。

### 7.3 状态迁移

| 当前状态 | 写入 | 动作 |
|---|---|---|
| 0 / 5 / 6 / 7 | 1 或 2 | 发选择（或本地置位），进入 1，寄存器清零 |
| 0 / 5 / 6 / 7 | 3 或 4 | 忽略（没有待确认的选择） |
| 1 | 任意 | 忽略，状态保持；选择往返很短，下游轮询后再试 |
| 2 | 3 | 发执行合，进入 4，寄存器清零 |
| 2 | 4 | 忽略，原因 6（确认与选择不符） |
| 2 | 1 | 忽略（重复请求同一方向） |
| 2 | 2 | 覆盖：取消当前选择，重新选择分，进入 1，不执行 |
| 3 | 4 | 发执行分，进入 4，寄存器清零 |
| 3 | 3 | 忽略，原因 6 |
| 3 | 2 | 忽略（重复请求） |
| 3 | 1 | 覆盖：取消当前选择，重新选择合，进入 1，不执行 |
| 4 | 任意 | 忽略，状态保持 |

“覆盖”只重新发起选择，不产生任何分合动作。设备侧同一 IOA 重新选择会替换旧选择；若现场设备不接受替换，需要先发撤销帧（COT=8），该行为作为兼容开关，默认关闭。

### 7.4 超时

- 进入状态 2 或 3 开始计时，30 秒内没有收到确认码 3 或 4：状态置 7，原因 2，清空本地选择；
- 进入状态 1 后由 104 的 t1 控制（默认 15 秒），无激活确认则状态 6，原因 2；
- 状态 4 的超时由 104 主站的 `CommandTimeout` 控制，超时后状态 6，原因 2。

### 7.5 与 104 两种模式的关系

| 桥接命令模式 | 写入 1 / 2 | 写入 3 / 4 |
|---|---|---|
| SelectAndExecute | 发 104 选择帧 | 发 104 执行帧 |
| Direct | 仅本地置状态，不发帧 | 发 104 直接执行帧 |

两种模式下 Modbus 侧的交互完全一致，切换只影响桥接层内部是否真的发选择帧。现场设备不支持选择时用 Direct，否则用 SelectAndExecute。

### 7.6 执行与回写

```
SingleCommandAsync(ioa, on, mode)
  成功       → 状态 5
  否定确认   → 状态 6，原因 1
  超时       → 状态 6，原因 2
  链路异常   → 状态 6，原因 3
```

执行在后台任务中进行，Modbus 请求线程只负责受理和置“执行中”，绝不能在事件回调里同步等待遥控完成，否则会把 Modbus 服务端的消息处理线程占住数秒。

### 7.7 安全约束

- `EnableCommands` 默认 false，关闭时命令寄存器写入只置状态 8，原因 4，不动作；
- 可选 IOA 白名单，未列出的点返回原因 5；
- 命令模式（Direct / SelectAndExecute）与现场设备能力对齐，见 7.5；
- 每次命令写一条审计日志：时间、IOA、命令值、结果、原因；
- 已知限制：核心库的 `DataStoreWrittenTo` 不带客户端标识，无法记录来源 IP。需要溯源时，只能通过服务器连接事件与时间窗关联。

## 8. 关键实现约束

| 约束 | 说明 |
|---|---|
| `WriteHoldingRegistersDirect` 已开放为 public | 同时开放 `WriteCoilsDirect`、`WriteInputDiscretesDirect`、`WriteInputRegistersDirect`；批量写一次持锁，避免 1636 个寄存器逐个加锁 |
| 批量写会触发 `DataStoreWrittenTo` | 命令监听只处理命令区，其他区忽略；命令寄存器清零写 0 也不会再次触发动作 |
| float 跨寄存器非原子 | 批量写在 `SyncRoot` 内完成，但服务端读处理是逐索引读取、不持 `SyncRoot`，理论上仍可能读到半新半旧；第一版接受，预留扩展点 |
| unitId 过滤 | `ModbusTcpServer.SlaveId` 默认 1，请求 unitId 不匹配会被静默丢弃，需与会话配置一致 |
| 寄存器单次上限 | 读保持寄存器最多 125 个，1636 个寄存器需要 14 次请求 |
| 502 端口权限 | Linux 下低于 1024 的端口需要特权，部署文档要写明 |

## 9. 测试方案

### 9.1 单元测试

- 地址映射：298 遥信落在 0..297；818 遥测占 0..1635；4 个命令占 0..11；健康区 1000..1007。
- 转发号不连续、重复、越界时的校验与报错。
- float 编解码：正负零、极值、NaN、两种字序往返。
- 命令状态机：1/2 请求、3/4 确认的完整迁移表；覆盖请求不执行；确认与选择不符被忽略；状态 1 与 4 期间的写入被忽略；30 秒确认超时。

### 9.2 集成测试

用现有 `SlaveHarness`（104 从站 + 主站，1116 点）加桥接层，再用核心库 `ModbusTcpClient` 轮询：

1. 读 298 个离散输入，与 104 缓存逐点一致；
2. 读 14 批共 1636 个保持寄存器，拼回 float 后与缓存一致；
3. 改 104 从站的值，200ms 内 Modbus 侧可见；
4. 停 104 从站，健康区链路状态与刷新秒数按预期变化；
5. 写 1（请求合），状态先 1 后 2，命令寄存器回 0；再写 3（确认合），状态 5，104 从站收到遥控；
6. 待确认合时写 2（请求分），状态回到 1 再变 3，104 侧只收到选择、没有执行；
7. 待确认合时写 4（确认分），状态保持 2，原因 6，104 侧无动作；
8. 进入待确认后不写确认码，30 秒后状态 7；
9. 命令通道关闭时写入，状态 8、原因 4，104 侧无动作。

### 9.3 容量测试

3 个 Modbus 客户端同时以 1 秒周期轮询 1116 点，连续 10 分钟，检查异常率、CPU 与内存。

## 11. 风险与未决项

| 项 | 说明 | 处理 |
|---|---|---|
| float 撕裂 | 双寄存器非原子 | 第一版接受，保留子类化加锁方案 |
| 时标丢失 | Modbus 无时间语义 | 文档声明；需要时另开 104 |
| 双点降维 | 中间态丢失 | 文档声明 |
| 命令来源不可追溯 | 事件不带客户端 IP | 记录时间窗，必要时改造服务器 |
| 点表变更导致地址平移 | 转发号追加安全，插队不安全 | 启动打印版本哈希，变更人工确认 |
| 502 暴露面 | Modbus 无认证 | 默认只读；命令白名单；绑定内网 |

已定：断链时返回陈旧值，靠健康区告警，不让读请求返回异常码。

已定：命令编码 1/2 请求、3/4 确认，确认窗口 30 秒，待确认期间写不同请求值覆盖但不执行。

待定：桥接层默认用 Direct 还是 SelectAndExecute。两者 Modbus 交互一致，只影响是否真的发 104 选择帧；接现场主机后按设备能力定，建议优先 SelectAndExecute。

## 13. 两个容易忽略的现场事实

**周期写不会误确认。** 方案 B 下，PLC 每个扫描周期重复写 1 只会反复“请求合”，不会触发确认；只有写 3 才执行。这是方案 B 相对“同值写两次”的核心优势，部署文档必须写清楚。

**确认不是身份确认。** Modbus 无法标识客户端，A 请求、B 确认在协议层无法禁止。二次确认防的是误碰和误组态，不防人为串通；需要更强的约束只能靠操作票或上层系统。

## 12. 结论

这个桥接的价值是把 104 的实时性保留在采集侧，把兼容性交给 Modbus 侧，两边各取所需。代价是品质、时标、双点中间态这三类信息在 Modbus 侧不可表达，只能靠健康区与文档兜底。因此计划把“只读镜像”和“命令通道”拆成两个阶段：先让数据可信，再让操作可控。
